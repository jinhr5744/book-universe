데이터 모델

별은 판본이 아니라 저작이다

『1984』의 민음사 양장본과 문고본, Penguin 원서는 ISBN이 전부 다르다. ISBN 단위로 별을 만들면 같은 책을 읽은 세 사람이 서로 다른 별 셋으로 흩어진다. 겹침을 보겠다는 목표가 정면으로 깨진다.

소장 목록 안에서도 같은 일이 일어난다. 그리고 나중에 학술논문을 붙이면 arXiv 프리프린트와 학회 게재본에서 똑같은 문제가 반복된다. 그래서 저작(Work)과 판본(Edition)을 나눈다. 사용자는 검색에서 판본을 집지만, 하늘에 뜨는 별은 저작이다. 

Work  "인공지능 : 수학적 이해에서 알고리즘까지"  오상훈   ← 하늘에 뜨는 단위
 └ Edition  홍릉 2025 "개정판"  isbn13 9791156002635  pyxis 100838844
             ↑ Pyxis 가 edition 필드로 "개정판"을 준다.
               초판이 목록에 있다면 그건 별개 레코드다 — 합칠 자리가 여기다.

1단계에서는 레코드 하나가 Work 하나 + Edition 하나가 된다. 구조를 지금 만들어두는 이유는 나중에 넣을 수 없기 때문이다. 판본을 실제로 묶는 건 2단계, 원서와 번역본이 같은 별에 모이는 건 그다음이다.

중복 판정은 제약조건이 대신한다

식별자 테이블의 기본키를 (scheme, value_norm)으로 잡으면 “하나의 식별자는 하나의 별에만”이 애플리케이션 로직이 아니라 DB 불변식이 된다. 판정 코드에 버그가 있어도 데이터는 갈라지지 않는다.

자료유형 11종 중 하나만 뺀다

Pyxis가 /material-types로 전 11종을 내려준다. 검색 패널의 필터는 하드코딩하지 말고 이 엔드포인트로 채운다.

CR만 뺀다. 저널은 저작이 아니라 컨테이너다 — 논문 한 편과 저널 한 종이 같은 층위로 하늘에 뜨면 별자리의 의미가 깨진다.

식별자에 권위 등급을 붙인다

소장자료만 다루면 DOI가 거의 없다. 그런데 학위논문·보고서·고서·오래된 자료는 ISBN도 없다. 이들을 ‘식별자 없는 자료’로 취급하면 아래 k-임계값에 걸려 영원히 우주에 뜨지 못한다.

소장 목록에 오른 자료는 사서가 목록을 만든 자료다. 실재가 이미 보증되어 있다. 그래서 Pyxis 레코드 ID를 authority='local' 식별자로 인정한다. 지킬 선은 두 개다 — global(ISBN·DOI)과 스키마 수준에서 구분하고, 나중에 ISBN이 발견되면 global 행을 추가해 그쪽을 우선한다. 다기관으로 넓힐 때 재정합이 필요한 것은 local 행뿐이다.

1단계에서는 유사도 매칭을 끈다

단일 도서관 목록이라 한 자료 = 한 레코드다. Pyxis 레코드 1개 = Work 1개 + Edition 1개. 자동 병합 없음. 같은 자료를 두 사람이 등록하면 식별자가 충돌하면서 자동으로 같은 별에 모인다 — 겹침은 그게 전부고, 애매한 판정이 없다.

유사도를 스키마에 남겨두는 건 역할이 바뀌기 때문이다. 중복 제거에서 판본 묶기로 — 『인공지능』 2018년판과 2025 개정판은 Pyxis에 별개 레코드로 존재하고, 이들을 한 별로 모으는 일이 남는다. 틀려도 두 별이 하나로 합쳐질 뿐이고 되돌릴 수 있지만, 1단계부터 자동으로 켜면 오병합 리스크만 지고 얻는 게 적다. 인스펙터에 “이 책은 저 별과 같은 책이에요” 버튼만 두어 제안을 모아둔다.

프라이버시 경계

저장은 신원째로, 표시는 집계만

익명으로 수집하는 게 아니다. 누가 무엇을 등록했는지는 DB에 그대로 남는다 — 그래야 “우주에서 내 위치”를 계산할 수 있고, 탈퇴할 때 그 사람 몫만 정확히 뺄 수 있다. 가리는 일은 표시 시점에 일어난다.

설계의 급소

가리는 작업을 클라이언트나 서버 코드에서 하면 안 된다. 클라이언트에서 가리면 API 응답에 user_id가 그대로 실려 오고, 서버 코드에서 가리면 언젠가 엔드포인트를 하나 추가하면서 빠뜨린다.

DB 경계에 박아두면 신원 컬럼이 공개 질의 결과에 애초에 존재할 수 없다.

가려도 추론된다 — k-임계값

user_id를 완벽히 가려도 집계 자체에서 역추론이 된다. 희귀한 논문 두 편을 잇는 선이 1인짜리로 떠 있으면 그 분야 사람들은 누군지 안다. 연결은 “읽었다”보다 훨씬 사적인 정보다 — 그 사람의 생각이기 때문에.

밝기도 원시값으로 내보내지 않는다. 1–5 등급으로 구간화해서 1명과 2명이 같은 계급이 되게 한다. 항성 등급이 원래 로그 스케일이라 별자리 은유와도 맞는다.

1단계에서는 모든 소장자료가 식별자를 갖기 때문에 두 번째 행(2명부터)이 사실상 잠든다. 그 분기는 웹문서를 넣는 시점에 되살아난다 — 조건을 지금 심어두고 나중에 깨우는 편이, 나중에 급히 끼워넣는 것보다 안전하다.

제약이 만든 기능

임계값에 못 미친 내 별은 우주에 없지만, 로그인한 나에게만 희미하게 그려준다. 좌표는 내가 그 별과 이어둔 다른 별들의 무게중심 근처에 띄우고 “아직 당신만 보고 있는 별” 배지를 단다. 두 번째 사람이 등록하는 순간 별이 점화되어 우주에 등재된다 — 이 서비스에서 가장 기분 좋은 순간이 된다.

소장자료만 쓰면 막힌 곳이 하나도 없다. Pyxis는 우리 도메인이고 외부 자격증명 대기가 없다. 그리고 벤더 메타데이터 라이선스 제약도 없다 — 소장 목록은 우리 데이터이므로 MARC 520 초록까지 저장할 수 있다. EBSCO를 붙이는 순간 생기는 “초록은 저장하지 말 것” 제약이 1단계에는 아예 없다.

관측된 엔드포인트 — 전부 우리 도메인

GET /pyxis-api/1/collections/1/search?all=k|a|인공지능&max=20&offset=0
GET /pyxis-api/1/biblios/{id}                      ← MARC 원본 전체
GET /pyxis-api/1/material-types                    ← 자료유형 11종
GET /pyxis-api/collections/1/auto-completions/{q}  ← 검색 패널에 그대로
GET /pyxis-api/1/outer-biblio-images-by-isbn/{isbn13}

관측 시점에 인증 없이 응답했다. 그래도 서비스에서는 서버 프록시를 경유한다 — 레이트리밋과 캐시를 우리가 걸고, 나중에 EDS를 붙일 때 클라이언트 코드를 건드리지 않게 된다.

어댑터

검색은 도서관에서, 정체성은 식별자로

Pyxis 레코드 ID(100838844)를 별의 정체성으로 쓰면 안 된다. 다른 학교로 넓히는 순간 같은 논문이 학교마다 다른 별이 되고, 도서관이 시스템을 교체하면 누적된 별자리가 통째로 고아가 된다. 로컬 ID는 access_links에만 넣는다 — 이 테이블을 통째로 지워도 별자리는 멀쩡하다.

KORMARC 245 원문이 그대로 온다. 세 가지가 섞여 있다. 

"(한국인이 알아야 할) 인공지능"            → 괄호 접두는 제목이 아니다
"인공지능 : 수학적 이해에서 알고리즘까지"    → " : " 이후는 부제
"인공지능 / 이건명 지음"                   → " / " 이후는 책임표시

title에는 본제목만 넣고, title_norm에는 부제를 넣지 않는다 — 부제 유무가 유사도를 흔들어서, 2단계 판본 묶기에서 바로 문제가 된다. 검색 응답의 author도 제1저자뿐이라 전체 저자는 MARC 100·700에서 가져와야 한다.

초기 추천을 부트스트랩할 재료가 이미 있다

Pyxis 검색 응답의 similars[]는 벤더가 이미 계산해 둔 유사자료다. 우주가 비어 있는 초기에는 “한 칸 옆” 추천의 재료가 없으므로 그동안 이 값을 쓰고, 사용자가 쌓이면 universe_edges 기반으로 갈아탄다.

  • 남의 메모 · 남의 좌표 (애초에 공개 출구에 없다)

등록 동선

드롭하면 먼저 놓이고, 나중에 채워진다

카드를 캔버스에 떨어뜨리는 순간 회색 노드가 그 자리에 먼저 놓인다. 서버 응답을 기다리지 않는다. resolve가 끝나면 실제 데이터로 채워지며 별이 점화된다. 

Pyxis 검색 카드 ──드래그──▶ 캔버스 드롭 (좌표 확보)
                              │
              식별자 추출  isbn13 (있으면) + pyxis:pnu (항상)
                              │
                    work_identifiers 조회
                       ├ HIT  ─────▶ 기존 별에 합류   이미 누가 등록한 자료
                       └ MISS ─────▶ GET /biblios/{id} MARC 상세
                                       └▶ works 1 + editions 1  새 별
                              │
              access_links 기록 (청구기호·소장처·대출상태) ──▶ 노드 생성

애매한 판정이 없다. 같은 자료를 두 사람이 등록하면 식별자가 충돌하면서 자동으로 같은 별에 모이고, 그게 겹침의 전부다. 2단계에서 판본 묶기를 켤 때 — 그때 비로소 “혹시 같은 책인가요?”를 묻는 확인 대기 상태가 들어온다.

연결 그리기

노드 테두리의 앵커를 끌어 다른 노드에 떨어뜨리면 관계 타입을 고른다 — 인용함 · 반박함 · 같은주제 · 방법론차용 · 후속연구. 다섯 개 고정이다. 자유 입력을 허용하면 전역 집계가 불가능해진다.

순서

우주는 나중에 얹어도 된다

1단계에서 전역 화면을 만들지 않아도 데이터는 이미 쌓인다. 집계 뷰는 나중에 얹어도 그동안의 등록이 전부 반영된다.

  1. 내 서재 + Pyxis 어댑터 + resolve(1:1) 외부 의존이 하나도 없다. 확인할 것 — 드래그해서 별을 놓는 게 재미있는가.
  2. 집계 뷰 + 배치 레이아웃 + 전체 유니버스 확인할 것 — 군집이 눈에 보이기 시작하는가. 같은 학교라 50명이 분기점이 된다.
  3. 내 위치 오버레이 + 한 칸 옆 추천 확인할 것 — “당신의 하늘은 여기입니다” 순간이 먹히는가.
  4. 판본 묶기 (유사도 ON) + 성단 이름 투표 사용자 제안이 쌓인 뒤에 켠다. 확인할 것 — 판본이 합쳐지면 겹침이 더 선명해지는가.
  5. EDS 편입 (학술논문) · 웹문서 등록 여기서 처음으로 외부 자격증명이 필요해진다. 범위를 넓힐 값이 확인된 뒤에 간다.
범위를 좁혀서 얻는 것

전 세계를 대상으로 열면 초기 사용자 50명이 각자 다른 자료를 등록해 별이 전부 흩어지고, 겹침이라는 핵심 기능이 화면에 아예 나타나지 않는다. 같은 학교면 정반대다 — 같은 수업, 같은 지도교수, 같은 학과. 읽는 자료가 겹칠 확률이 압도적으로 높다.

다음 할 일

막힌 곳이 없다

범위를 소장자료로 줄이면서 유일한 외부 의존이던 EBSCO 자격증명이 5단계로 밀렸다. 1단계를 시작하기 위해 기다려야 할 것은 아무것도 없다. 남은 건 우리가 정하는 일들뿐이다.

  • Pyxis all=필드|연산자|값 문법의 필드 코드 전수 확인 (벤더 문서) — 제목·저자 한정 검색에 필요
  • Pyxis 상세 페이지 URL 패턴 확정 — 인스펙터의 “도서관에서 보기” 목적지
  • 교내 SSO 연동 — 학번은 salt+hash로만, 소속은 단과대 수준까지만
  • 원본 테이블 직접 조회용 계정을 서비스 롤과 분리하고 감사 로그 연결
  • 개인정보 처리방침에 “식별 가능한 형태로 저장, 공개 화면에서는 집계로만 표시”로 정확히 기재
전산 담당자에게

대출·열람 이력을 자동으로 끌어오지 말 것. 도서관 이용 기록은 이용자 비밀보호 의무가 걸린 정보다. “내 대출 이력에서 별 가져오기”는 사용자가 매번 직접 누르는 명시적 가져오기로만 두고, 가져온 뒤에도 기본은 비공개여야 한다. 편의를 위해 자동 연동하고 싶은 유혹이 클 텐데, 이 서비스에서 유일하게 되돌릴 수 없는 사고가 날 수 있는 지점이다.
