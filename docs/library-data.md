# 도서관 데이터 읽는 규칙

`scripts/build_universe.py` 가 도서관 목록 데이터를 읽을 때 지키는 규칙.
전부 2026-09-16 실측에서 나온 것이고, 코드가 이대로 구현되어 있다.

이 문서는 **살아 있는 코드의 사양서**다. 규칙을 바꾸면 이 문서도 같이 고친다.

---

## 1. 자료유형 — 11종 중 하나만 뺀다

| code | 자료유형 | → 타입 | 별이 되나 |
|---|---|---|---|
| `BK` | 단행본 | `book` | ✅ |
| `RB` | 고서 | `book` | ✅ |
| `ER` | 전자자료 | `book` | ✅ |
| `TH` | 학위논문 | `paper` | ✅ |
| `AT` | 기사 | `paper` | ✅ |
| `RP` | 보고서 | `paper` | ✅ |
| `MP` | 지도 | `media` | ✅ |
| `ML` | 음악/녹음자료 | `media` | ✅ |
| `VM` | 시청각자료 | `media` | ✅ |
| `MX` | 복합자료 | `media` | ✅ |
| `CR` | 연속간행물 | — | ❌ **제외** |

`CR` 을 빼는 이유: **저널은 저작이 아니라 컨테이너다.** 논문 한 편과 저널 한 종이
같은 층위로 하늘에 뜨면 별자리의 의미가 깨진다.

> 함정: 검색 API 응답의 `materialType` 에는 `code` 가 없다 — `{id, name}` 만 온다.
> `code` 는 `/material-types` 와 서지 상세에만 있다. DB 를 직접 읽는 지금 경로에서는
> `MATERIAL_TYPE.CODE` 를 조인하므로 문제가 없지만, API 를 다시 붙이면 id → code
> 대응표가 필요하다.

## 2. 제목 — `TITLE_STATEMENT` 는 KORMARC 245 원문이다

세 가지가 섞여 있어서 그대로 쓰면 안 된다.

```
"(한국인이 알아야 할) 인공지능"             → 괄호 접두는 제목이 아니다
"인공지능 : 수학적 이해에서 알고리즘까지"     → " : " 이후는 부제
"인공지능 :튜링 테스트에서 딥러닝까지"        → 콜론 뒤 공백이 없는 레코드도 있다
"인공지능 / 이건명 지음"                    → " / " 이후는 책임표시
```

**분해 순서**: 책임표시(`" / "`) → 괄호 접두 → 부제(첫 콜론).
공백 없는 `/` 는 제목에 포함된 슬래시일 수 있으므로 건드리지 않는다.

부제는 표시용으로만 쓴다. 유사도 비교에 쓸 정규화 형태에는 **부제를 넣지 않는다** —
부제 유무가 레코드마다 달라서 유사도를 흔든다.

아직 처리하지 않은 것: `"인공지능 = Artificial Intelligence"` 의 ` = ` 병기제목.

## 3. 저자 — `ALL_AUTHOR` 는 JSON 배열 문자열이다

```
원본   ["한강","한강 지음"]
       ["Kreyszig, Erwin","서진현","심양보","이상구","유일","박현덕","양영균","김의택"]

처리   한강
       Kreyszig, Erwin · 서진현 · 심양보
```

배열을 풀고 → 역할어(`지음·엮음·옮김·저·편·역·공저·편저·글·그림·외`)를 떼고 →
공백 무시 중복 제거(`한강` 과 `한강 지음` 은 같은 사람) → 최대 3명까지 표시.

그대로 쓰면 화면에 배열 원문이 노출된다. 실제로 한동안 그렇게 나가고 있었다.

---

## 4. 청구기호 — DDC 이고, 두 체계가 섞여 있다

보유율 96.4%. MARC 태그로 보면 **97% 가 082(DDC)** 이고 056(KDC)만 있는 건 0.9%다.

다만 실제 값에는 두 체계가 섞여 있다.

```
회계원리     657      (DDC)  /  325.9    (KDC)
인공지능     006.3    (DDC)  /  569.93   (KDC)
```

오래된 자료가 KDC 시절 번호를 갖고 있다. **첫 자리를 그대로 주제로 쓰면 같은 주제가
다른 구역으로 흩어진다.** 현재 배치는 청구기호를 쓰지 않으므로 문제가 없고,
주제 좌표를 도입할 때 이 점을 처리해야 한다.

전체 분포(DDC 대분류): 300 사회과학 20.9% · 800 문학 19.8% · 600 기술·의학·경영 17.8% ·
100 철학·심리 12.6% · 500 자연과학 6.9% · 700 예술 6.6% · 000 총류·컴퓨터 6.5% ·
900 역사 4.6% · 400 언어 3.3% · 200 종교 1.1%

## 5. 초록은 거의 없다

MARC 520 보유율 **1.9%** (표본 3,000종 중 58종).

소장 목록은 우리 데이터라 저장에 라이선스 제약이 없지만, **데이터 자체가 없다.**
자료의 의미를 다루려면 제목·부제·저자·출판사·청구기호로만 해야 한다.

## 6. 중복 목록 레코드가 존재한다

```
「새마을 運動 10年史」  ↔  「새마을運動 10年史」      띄어쓰기만 다름
도용태 『인공지능』 사이텍미디어 2001                   같은 ISBN 으로 두 레코드
```

같은 ISBN 을 가진 레코드가 둘 이상 있을 수 있다. 화면에서 목록 항목의 키로 ISBN 을
쓰면 항목이 사라진다 — **레코드 ID 를 키로 써야 한다.**

동시등장 그래프가 이런 중복을 자동으로 드러낸다(둘 다 담은 사람이 있어서 선으로 이어진다).
목록 정비 재료로 쓸 수 있다.

---

## 7. 식별자를 다룰 때 (현재 코드에는 없음)

지금은 레코드 ID 로만 자료를 구분한다. 개인 계층을 붙여 여러 기관·판본을 다루게 되면
`docs/schema.sql` 의 `work_identifiers` 설계를 따른다. 요점만:

- 별의 정체성은 **공적 식별자**(ISBN-13 · DOI · arXiv)로만 결정한다
- ISBN-10 은 반드시 13 으로 변환해 저장한다 — 같은 책이 두 별로 갈라지는 최대 원인
- 도서관 레코드 ID 는 `authority='local'` 로 구분해 인정한다. 학위논문·보고서·고서는
  ISBN 이 없어서, 이걸 인정하지 않으면 영원히 우주에 뜨지 못한다
- 레코드 ID 는 정체성이 아니라 **접근 경로**다. 시스템을 교체해도 별자리는 남아야 한다

## 넓힐 때

통합검색 화면은 네 시스템의 합성이다 — 소장자료(자체 ILS) · 학술논문 · 전자저널·전자책 ·
추천 학술DB. 지금은 소장자료만 쓴다.

학술논문 쪽을 붙이면 DOI 가 대량으로 들어와서 식별자 문제가 크게 풀린다.
기관별 프로파일 값과 관측 기록은 `docs/institution.local.md` (커밋되지 않음) 에 있다.
